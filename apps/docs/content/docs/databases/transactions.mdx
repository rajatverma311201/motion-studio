## Chapters and voiceover notes

### 01 · INTRO

<VoiceoverNotes>

- A transaction groups many steps into one unit: all of them happen, or none do.
- The bank transfer makes the cost of a half-finished unit visible.
- Think of it as one promise that covers several writes.
- By the end you will know what ACID, isolation levels and the WAL actually guarantee.

</VoiceoverNotes>

A transaction groups many writes into one unit: all happen, or none do. The bank transfer makes the cost of a half-finished unit visible.

### 02 · THE PROBLEM

<VoiceoverNotes>

- Alice sends ₹300 to Bob. In SQL that is two separate UPDATE statements.
- Step one debits Alice. The server dies before step two runs.
- Bob never receives the money, and the books no longer add up.
- The database is now inconsistent. We need all-or-nothing.
- Ask yourself what the balances should be after the crash.

</VoiceoverNotes>

Two separate `UPDATE` statements lose ₹300 when the server dies between them. The money leaves Alice and never reaches Bob, so the books no longer add up.

### 03 · BEGIN · COMMIT · ROLLBACK

<VoiceoverNotes>

- Wrap both updates in BEGIN and COMMIT, and they become one transaction.
- Inside the transaction the changes are pending; nobody else treats them as final.
- COMMIT makes both changes permanent at the same instant.
- Replay the crash before COMMIT: the database notices the unfinished transaction.
- ROLLBACK undoes every pending change, as if nothing happened.

</VoiceoverNotes>

```sql
BEGIN;
UPDATE accounts SET bal = bal - 300 WHERE id = 'alice';
UPDATE accounts SET bal = bal + 300 WHERE id = 'bob';
COMMIT;
-- or, if anything fails: ROLLBACK;
```

<Callout type="warn" title="Two updates, no transaction">
  A crash between the statements leaves the database inconsistent. Wrap them in one transaction.
</Callout>

### 04 · ACID

<VoiceoverNotes>

- ACID is four guarantees that make a database transaction trustworthy.
- Atomicity: a failure anywhere undoes the whole transaction.
- Consistency: every commit leaves the data valid under the rules.
- Isolation: concurrent transactions behave as if they ran separately.
- Durability: a committed change survives a crash.
- Atomicity and durability cover crashes; isolation covers concurrency.

</VoiceoverNotes>

Atomicity undoes a failed transaction; consistency rejects a change that breaks a constraint; isolation keeps concurrent work apart; durability keeps a committed change on disk.

### 05 · ISOLATION ANOMALIES

<VoiceoverNotes>

- A dirty read uses a value another transaction has not committed and may still roll back.
- A non-repeatable read sees the same row change inside one transaction.
- A phantom read sees a new row appear in a repeated range query.
- Show T1 and T2 touching the same data at the same time.
- These anomalies are exactly what isolation levels exist to prevent.

</VoiceoverNotes>

A dirty read uses an uncommitted value that is later rolled back. A non-repeatable read sees the same row change inside one transaction, and a phantom read sees new rows appear in a repeated range.

### 06 · ISOLATION LEVELS

<VoiceoverNotes>

- The SQL standard defines four levels, each blocking more anomalies.
- Read Uncommitted allows all three; Read Committed blocks dirty reads.
- Repeatable Read keeps read rows stable; Serializable behaves as if transactions ran one at a time.
- More isolation means less concurrency, so pick the weakest safe level.
- Defaults differ: PostgreSQL uses Read Committed, MySQL InnoDB uses Repeatable Read.
- PostgreSQL's Repeatable Read also blocks phantoms, even though the standard does not require it.

</VoiceoverNotes>

| Level            | Dirty read | Non-repeatable read | Phantom read |
| ---------------- | ---------- | ------------------- | ------------ |
| Read Uncommitted | possible   | possible            | possible     |
| Read Committed   | prevented  | possible            | possible     |
| Repeatable Read  | prevented  | prevented           | possible     |
| Serializable     | prevented  | prevented           | prevented    |

<Callout type="warn" title="Always choosing Serializable">
  More isolation means less concurrency. Pick the weakest level that is safe.
</Callout>

<Callout type="warn" title="Assuming every engine has the same default">
  PostgreSQL defaults to Read Committed; MySQL InnoDB to Repeatable Read.
</Callout>

### 07 · DURABILITY · WAL

<VoiceoverNotes>

- Writing every change straight to data files would be slow random I/O.
- The change first lands in memory, on a cached page.
- Before COMMIT returns, the log records are appended to the WAL and flushed.
- Only then does the client hear COMMIT OK, so the commit is durable.
- On a crash, memory is wiped but the log survives; the database replays committed changes.

</VoiceoverNotes>

Changes first land in memory on a cached page. Before `COMMIT` returns, the log records are appended to the write-ahead log and flushed; after a crash, the database replays every committed change from that log.

### 08 · IN CODE

<VoiceoverNotes>

- In Quarkus one annotation gives you all of this: @Transactional.
- The interceptor starts a transaction before the method and commits after it returns.
- A runtime exception rolls back the whole transaction.
- Checked exceptions do not roll back by default; opt in with rollbackOn.
- Keep transactions short so locks are held for as little time as possible.

</VoiceoverNotes>

```java
@ApplicationScoped
public class TransferService {
  @Transactional
  public void transfer(long from, long to, BigDecimal amount) {
    accounts.debit(from, amount);
    accounts.credit(to, amount);
  }
}
```

<Callout type="warn" title="Expecting a checked exception to roll back">
  In Quarkus, a checked exception still commits by default. Opt in with `@Transactional(rollbackOn = …)`.
</Callout>

<Callout type="warn" title="Holding a transaction open">
  Locks are held until the transaction ends. Keep HTTP calls and sleeps outside it.
</Callout>

### 09 · RECAP

<VoiceoverNotes>

- Four guarantees, one idea: group the steps and treat them as a single unit.
- A transaction either fully happens or never happened.
- Atomicity and durability cover crashes; isolation covers concurrent readers and writers.
- In Quarkus, @Transactional is the boundary; keep it short.
- Next lesson: how an index finds one row among millions.

</VoiceoverNotes>

The four guarantees reduce to one idea: group the steps and treat them as one unit. A transaction either fully happens or never happened.

| Concept                  | One-line rule                                                 | When it matters                     |
| ------------------------ | ------------------------------------------------------------- | ----------------------------------- |
| Transaction              | All steps happen, or none do.                                 | Multi-statement writes.             |
| COMMIT                   | Makes pending changes permanent at one instant.               | After the last write.               |
| ROLLBACK                 | Undoes every pending change.                                  | On failure or a failed check.       |
| Atomicity                | A failure anywhere undoes everything.                         | Crashes mid-transaction.            |
| Isolation                | Concurrent transactions behave as if separate.                | Two writers touching the same rows. |
| Durability / WAL         | Log flushed before COMMIT returns.                            | Crash recovery.                     |
| Quarkus `@Transactional` | Runtime exceptions roll back; checked ones commit by default. | Service methods.                    |
