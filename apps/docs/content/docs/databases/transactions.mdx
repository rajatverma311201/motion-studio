## The idea in one minute

A bank transfer is two writes: debit Alice ₹300, credit Bob ₹300. If the server dies between them, the money leaves Alice and never reaches Bob, so the books no longer add up. A transaction groups the writes so they all happen or none do: `COMMIT` makes every pending change permanent at one instant, and `ROLLBACK` undoes them as if nothing happened. Atomicity and durability cover crashes; isolation covers concurrent transactions and the dirty, non-repeatable, and phantom reads they can cause. The isolation levels decide how much of that is allowed, trading concurrency for safety. Durability comes from the write-ahead log, flushed before `COMMIT` returns so a restart can replay the change. In code, Quarkus wraps a method in a transaction with `@Transactional`.

## Chapter notes

### 1. Intro

A transaction groups many steps into one unit: all happen, or none do. The bank transfer makes the cost of a half-finished unit visible.

### 2. The problem

Alice sends ₹300 to Bob in two `UPDATE` statements. Step 1 debits Alice, the server dies before step 2, and Bob never receives the money, so the books no longer add up.

### 3. BEGIN · COMMIT · ROLLBACK

Wrapping both updates in `BEGIN … COMMIT` makes them one transaction. Changes stay pending, `COMMIT` makes both permanent at the same instant, and `ROLLBACK` undoes everything if the crash arrives first.

```sql
BEGIN;
UPDATE accounts SET bal = bal - 300 WHERE id = 'alice';
UPDATE accounts SET bal = bal + 300 WHERE id = 'bob';
COMMIT;
-- or, if anything fails: ROLLBACK;
```

### 4. ACID

Atomicity undoes a failed transaction; consistency rejects a change that breaks a constraint; isolation keeps concurrent work apart; durability keeps a committed change on disk. Atomicity and durability cover crashes, isolation covers concurrency.

### 5. Isolation anomalies

A dirty read uses an uncommitted value that is later rolled back. A non-repeatable read sees the same row change inside one transaction, and a phantom read sees new rows appear in a repeated range.

### 6. Isolation levels

Read Uncommitted allows all three anomalies, Read Committed blocks dirty reads, Repeatable Read keeps read rows stable, and Serializable behaves as if transactions ran one at a time. More isolation means less concurrency, so pick the weakest safe level; PostgreSQL defaults to Read Committed and MySQL InnoDB to Repeatable Read. The table is the SQL-standard view, and PostgreSQL's Repeatable Read also blocks phantoms.

| Level            | Dirty read | Non-repeatable read | Phantom read |
| ---------------- | ---------- | ------------------- | ------------ |
| Read Uncommitted | possible   | possible            | possible     |
| Read Committed   | prevented  | possible            | possible     |
| Repeatable Read  | prevented  | prevented           | possible     |
| Serializable     | prevented  | prevented           | prevented    |

### 7. Durability · WAL

Changes first land in memory on a cached page. Before `COMMIT` returns, the log records are appended to the write-ahead log and flushed; after a crash, the database replays every committed change from that log.

### 8. In code

`@Transactional` starts a transaction before the method and commits after it returns. A runtime exception rolls back, a checked exception commits by default, and `rollbackOn` opts in to rollback for checked exceptions; keep the boundary short.

```java
@ApplicationScoped
public class TransferService {
  @Transactional
  public void transfer(long from, long to, BigDecimal amount) {
    accounts.debit(from, amount);
    accounts.credit(to, amount);
  }
}
```

### 9. Recap

The four guarantees reduce to one idea: group the steps and treat them as one unit. A transaction either fully happens or never happened.

## Cheat sheet

| Concept                  | One-line rule                                                 | When it matters                     |
| ------------------------ | ------------------------------------------------------------- | ----------------------------------- |
| Transaction              | All steps happen, or none do.                                 | Multi-statement writes.             |
| COMMIT                   | Makes pending changes permanent at one instant.               | After the last write.               |
| ROLLBACK                 | Undoes every pending change.                                  | On failure or a failed check.       |
| Atomicity                | A failure anywhere undoes everything.                         | Crashes mid-transaction.            |
| Isolation                | Concurrent transactions behave as if separate.                | Two writers touching the same rows. |
| Durability / WAL         | Log flushed before COMMIT returns.                            | Crash recovery.                     |
| Quarkus `@Transactional` | Runtime exceptions roll back; checked ones commit by default. | Service methods.                    |

## Common mistakes

<Callout type="warn" title="Two updates, no transaction">
  A crash between the statements leaves the database inconsistent. Wrap them in one transaction.
</Callout>

<Callout type="warn" title="Expecting a checked exception to roll back">
  In Quarkus, a checked exception still commits by default. Opt in with `@Transactional(rollbackOn = …)`.
</Callout>

<Callout type="warn" title="Holding a transaction open">
  Locks are held until the transaction ends. Keep HTTP calls and sleeps outside it.
</Callout>

<Callout type="warn" title="Always choosing Serializable">
  More isolation means less concurrency. Pick the weakest level that is safe.
</Callout>

<Callout type="warn" title="Assuming every engine has the same default">
  PostgreSQL defaults to Read Committed; MySQL InnoDB to Repeatable Read.
</Callout>

## Try it yourself

These are examples you can run in a scratch PostgreSQL database, not output from the video.

```sql
-- example: move ₹300 or do nothing
BEGIN;
UPDATE accounts SET balance = balance - 300 WHERE id = 'alice';
UPDATE accounts SET balance = balance + 300 WHERE id = 'bob';
COMMIT;

-- example: change the isolation level for this transaction
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 'alice';
COMMIT;
```
