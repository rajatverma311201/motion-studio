## The idea in one minute

Without an index, the database reads every row and page: O(n). A sorted key list with row pointers enables binary search, O(log n), but keeping it sorted shifts entries on every insert. A tree avoids the shifting, yet a plain binary search tree can degenerate, and a balanced one still costs a disk read per level. Disks read whole pages, so a B-tree packs a node with hundreds of keys: a fanout near 500 puts ten million rows in three levels. A B+tree keeps every entry in linked leaves and uses internal nodes as signposts, so lookups are predictable and ranges walk sideways. Index what you query, and prove it with `EXPLAIN`.

## Chapter notes

### 1. Intro

A lookup is instant with an index, slow without one. The lesson moves from O(n) to O(log n).

### 2. Full table scan

`SELECT * FROM users WHERE name = 'Ria';` reads every row, and duplicate names mean it cannot stop early. Rows live on 8 KB pages, so the scan reads every page.

### 3. Sorted index

A sorted key-plus-pointer list enables binary search: 12 keys take four steps, ten million about 24. Inserting 50 shifts entries and rewrites pages.

### 4. Binary trees

Smaller keys go left, bigger right, so inserts need no shifting. Sorted input degenerates it into a linked list, and a balanced tree still reads one page per level.

### 5. Pages and fanout

Disks read whole 8 KB pages, so a node holds hundreds of keys. A fanout near 500 puts ten million rows in three levels; upper levels stay cached.

### 6. B-tree rules

A node is a sorted key list with one more child than keys. Leaves share a depth, ranges partition children, and non-root nodes stay half full.

### 7. B-tree search

Compare the key at each node; each visited node is one page read. A lookup can stop early in an internal node, and a miss still costs one node per level.

### 8. B-tree insert

Find the leaf, insert, and split when full. The tree grows only at the root, so leaves stay level, and splits cost extra writes.

### 9. B-tree vs B+tree

A B-tree puts keys and row pointers in every node. A B+tree keeps row pointers in the leaves, copies separators up, and links the leaves.

### 10. B+tree insert

A leaf split copies the separator up, so 15 stays in the parent and in the right leaf. Internal splits move the median, but leaves keep every key.

### 11. Lookup and range scan

A point lookup always reaches a leaf, so cost equals tree height. For a range, find the left edge and follow the leaf links right.

### 12. B+tree delete

Delete the key, then fix any too-empty node. A leaf borrows a spare key or merges with a neighbour; if the root loses its last child, the tree shrinks a level.

### 13. Why B+tree wins

Internal nodes hold only keys, so more fit per page and the tree is shallower. Lookups are predictable, ranges walk the leaves, and a full scan reads only the leaf level.

### 14. Clustered vs secondary

InnoDB's table is a B+tree sorted by primary key, with full rows in the leaves. A secondary index stores the key plus the primary key, so a lookup needs two walks unless it covers the query.

### 15. Composite indexes

An index on `(last_name, first_name)` sorts by last name, then first name inside each group. It serves `last_name` and both columns, not `first_name` alone; equality columns come first.

### 16. The cost of indexes

Every index is a B+tree kept in sync on writes, so five indexes mean five times the write work. Random UUIDv4 keys split at random and leave pages about 70% full.

### 17. EXPLAIN and gotchas

`EXPLAIN` shows `Seq Scan` versus `Index Scan`, and `EXPLAIN ANALYZE` adds timings. Indexes are ignored when a function wraps the column, a wildcard leads, types mismatch, selectivity is low, or indexes are too many.

```sql
EXPLAIN SELECT * FROM users WHERE email = 'ria@x.in';

-- illustrative PostgreSQL-style output
Seq Scan on users
  (cost=0.00..208334.00 rows=1)
  Filter: (email = 'ria@x.in')
```

### 18. Recap

Six cards close the lesson: sorted copy, B-tree, B+tree, secondary, composite, and cost. Index the queries you run and measure with `EXPLAIN`.

## Cheat sheet

| Concept         | One-line rule                                           | When it matters                     |
| --------------- | ------------------------------------------------------- | ----------------------------------- |
| Full scan       | No index reads every row and page, O(n).                | Large unindexed tables.             |
| B-tree          | Wide, shallow, balanced; nodes carry row pointers.      | Point lookups.                      |
| B+tree          | Entries in linked leaves; internal nodes are signposts. | Ranges and `ORDER BY`.              |
| Secondary index | Index, then primary key, then row.                      | InnoDB and PostgreSQL heap lookups. |
| Composite index | `(a, b)` serves `a` and `a + b`, not `b`.               | Multi-column filters.               |
| Index cost      | Every index slows writes and takes space.               | Write-heavy tables.                 |

## Common mistakes

<Callout type="warn" title="Function on the column">
  `LOWER(email)` cannot use an index sorted by raw email.
</Callout>

<Callout type="warn" title="Leading wildcard">
  `LIKE '%ria'` can match anywhere; `'ria%'` is one range.
</Callout>

<Callout type="warn" title="Type mismatch">
  Comparing text to a number can force a cast and skip the index.
</Callout>

<Callout type="warn" title="Too many indexes">
  Every write maintains every index. Drop the unused ones.
</Callout>

## Try it yourself

Scratch PostgreSQL examples:

```sql
CREATE TABLE users (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, email text NOT NULL);

INSERT INTO users (email)
SELECT 'user' || i || '@example.com' FROM generate_series(1, 100000) AS i;

EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'user42@example.com';
CREATE INDEX idx_users_email ON users (email);
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'user42@example.com';
```
